# Онлайн-игра: разбор текущей реализации

Это руководство описывает сетевой протокол и сервер онлайн-игры:
формат пакетов, подтверждения и повторы, регистрацию игроков и работу
с лобби и чатом. Оно предназначено для разработчика и подготовки к защите проекта.

Руководство описывает код из `feature/online-server`. Ветка
`feature/make-readme` хранит документацию и пока не содержит эту
реализацию. Для запуска сервера и его игровых тестов нужны также
`GameState`, `step`, `MovementError` и классы монстров из `dev`.
Команды ниже рассчитаны на версию проекта с обеими частями. Клиентская часть пока не реализована:
`minotaur/online/client.py` пуст. Протокол и сервер от неё не зависят.

## Формат пакета

Каждый пакет занимает одну строку JSON в UTF-8. `encode_packet` кодирует
словарь через `json.dumps(..., ensure_ascii=False)`, а `sendline` добавляет
перевод строки.

Пакет состоит ровно из шести полей:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `num` | целое число от 1 | Номер запроса. По нему находится подтверждение и распознаётся повтор. |
| `type` | `"req"` или `"resp"` | Запрос или ответ-подтверждение. |
| `topic` | `"system"`, `"lobby"`, `"game"` или `"chat"` | Область команды. |
| `cmdid` | непустая строка | Название команды, например `hello`, `join` или `update`. |
| `id` | непустая строка | ID игрока: первые шесть символов MD5 от ника. |
| `data` | JSON-объект | Параметры команды или результат ответа. |

Пример запроса и ответа на регистрацию:

```json
{"num": 1, "type": "req", "topic": "system", "cmdid": "hello", "id": "6a0613", "data": {"nick": "Max"}}
{"num": 1, "type": "resp", "topic": "system", "cmdid": "hello", "id": "6a0613", "data": {"ok": true}}
```

`read_packet` проверяет все поля. Лишние или отсутствующие поля, неверный
тип пакета, неизвестный топик, неположительный `num`, пустые `cmdid`/`id`
и `data`, не являющийся объектом JSON, приводят к `PacketError`, который перехватывается в `receive`.
При таймауте чтения функция возвращает `None`, при закрытом соединении
возникает `EOFError`.

## Как устроен обмен

1. Клиент вызывает `Protocol.request(...)`. Метод берёт следующий `num`,
   отправляет пакет `req` и сохраняет его в `pending` вместе с ID, топиком,
   числом отправок и сроком ожидания.
2. Сервер читает запрос в `Protocol.receive(...)`, передаёт его обработчику
   и получает пару `(cmdid, data)`. Ответ `resp` собирается с теми же
   `num`, `topic` и `id`, что и запрос. Поле `cmdid` может отличаться:
   например, на `ping` можно ответить `pong`.
3. Получив `resp` с ожидаемым `num`, `id` и `topic`, клиент удаляет запрос
   из `pending` и возвращает пакет из `receive`.
4. Если подтверждение не пришло за `timeout` (по умолчанию 1 секунда),
   запрос отправляется повторно. Всего делается не больше `attempts`
   отправок (по умолчанию 3, включая первую). После последней неудачной
   попытки соединение закрывается, а `receive` выбрасывает `TimeoutError`.
5. Повторный входящий запрос с тем же `num` и тем же содержимым получает
   сохранённый ответ. Обработчик при этом повторно не вызывается. Если
   под тем же номером пришёл другой запрос, возвращается отказ
   `NumAlreadyUsed` с подсказкой `next_num`. Прежний ответ сохраняется.

Ответы на входящие запросы хранятся в `Protocol.answers` до конца
соединения. Это нужно, чтобы отличить повтор от нового запроса и не
выполнить команду дважды.

## Разбор протокола

### `encode_packet(packet)` (`minotaur/online/protocol.py`)

Кодирует словарь пакета в байты JSON в UTF-8. Перевод строки не добавляет:
его добавляет `sendline` или тест. Если в данных есть значение, которое
JSON не поддерживает, возникает `TypeError`; циклическая ссылка приводит
к `ValueError`.

### `read_packet(tube, timeout)` (`minotaur/online/protocol.py`)

Читает одну строку через `recvuntil(b"\n", timeout=timeout)`, декодирует
UTF-8 и проверяет структуру пакета. Возвращает словарь с полями `num`,
`type`, `topic`, `cmdid`, `id` и `data`. Если за отведённое время строка
не получена, возвращает `None`.

### `Protocol(tube, timeout=1, attempts=3)`

Объект протокола для одного соединения. Хранит:

| Поле | Содержимое |
| --- | --- |
| `tube` | Соединение `pwntools`. |
| `timeout` | Ожидание пакета и интервал до повтора в секундах. |
| `attempts` | Максимальное число отправок запроса, включая первую. |
| `next_num` | Номер следующего исходящего запроса. Начинается с 1. |
| `pending` | Свои запросы, ожидающие ответа: байты, ID, топик, число отправок и срок. |
| `answers` | Ответы на входящие запросы по номерам. Нужны для повторной отправки ACK. |

Конструктор проверяет, что `timeout > 0`, а `attempts >= 1`.

### `request(topic, cmdid, player_id, data)`

Формирует пакет `req`, отправляет его и возвращает номер запроса. Запрос
остаётся в `pending` до получения подходящего `resp` или до исчерпания
попыток. Новый номер берётся из `next_num`.

### `receive(handle_request, player_id="unknown")`

Принимает один входящий пакет и обслуживает таймауты уже отправленных
запросов. Ошибку входящего пакета сообщает через запрос `system.error`.
До регистрации в таком уведомлении используется `id="unknown"`.

Для входящего `req`:

1. Если номер ещё не встречался, вызывается `handle_request(packet)`.
   Обработчик возвращает `(cmdid, data)`.
2. Собирается и отправляется `resp` с теми же `num`, `topic` и `id`.
3. Готовый ответ сохраняется в `answers`. Повтор того же пакета получит
   его без повторного вызова обработчика.

Для входящего `resp`:

1. Пакет ищется в `pending` по номеру.
2. Проверяются `id` и `topic`.
3. При совпадении запись удаляется, а пакет возвращается вызывающему коду.
   Если номер неизвестен или поля не совпали, возвращается `None`.

После обработки пакета `receive` проходит по `pending` и повторяет
запросы, у которых истёк срок. Если запрос уже отправлялся `attempts` раз,
соединение закрывается и возникает `TimeoutError`.

## Разбор сервера

### `Session`

`Session` создаётся на каждое TCP-соединение и хранит:

| Поле | Содержимое |
| --- | --- |
| `server` | `GameServer`, который обслуживает соединение. |
| `player_id` | ID игрока после `hello` или `None` до регистрации. |
| `finished` | Получен `disconnect`; цикл соединения должен завершиться. |
| `lobby_id` | Номер текущего лобби или `None`. |
| `updates` | Очередь снимков лобби, которые нужно отправить этому клиенту. |
| `chat_updates` | Пары `(cmd, data)` для отправки `chat.recv` и `chat.history`. |
| `game_updates` | Снимок игры для отправки этому участнику через `game.update`. |
| `start_updates` | Пары `(cmd, data)` для отправки `lobby.prepare`, `lobby.generate` и `lobby.level`. |

`Session.handle_request(packet)` обрабатывает один запрос:

1. `system.hello` проверяет ник и ID. Ник должен быть непустой строкой.
   ID обязан совпадать с первыми `PLAYER_ID_LENGTH` символами MD5 от ника.
   Успешная регистрация закрепляет ID за соединением.
2. До `hello` любая другая команда получает ответ
   `{"ok": false, "error": "Сначала отправьте hello.", "error_code": "HelloRequired"}`.
3. Поле `id` в каждом следующем запросе должно совпадать с ID соединения.
   Иначе возвращается `{"ok": false, "error": "ID принадлежит не вам.", "error_code": "WrongPlayerId"}`.
4. Команды `lobby` передаются в `GameServer.lobby_command`,
   команды `chat` в `GameServer.chat_command`, а `game` в `GameServer.game_command`.
5. `system.disconnect` снимает регистрацию, ставит `finished = True`
   и возвращает `{"ok": true}`.
6. Остальные команды получают ответ `{"ok": false, "error": "Неизвестная команда.", "error_code": "UnknownCommand"}`.

ID выводится из ника и проверяется сервером, но не является паролем или
защитой от подмены: это идентификатор для игрового протокола, а не
аутентификация.

### `GameServer`

`GameServer` хранит общие данные сервера:

| Поле | Содержимое |
| --- | --- |
| `players` | Ники зарегистрированных игроков по ID. |
| `sessions` | Активные сеансы по тем же ID. |
| `lobbies` | Лобби по номерам. Внутри хранятся имя, хозяин и участники. |
| `histories` | Списки сообщений по номерам лобби. |
| `next_lobby_id` | Номер следующего создаваемого лобби. |
| `lock` | Блокировка общих данных игроков и лобби. |

`register(session, player_id, nick)` добавляет игрока, если соединение ещё
не зарегистрировано и ID свободен. Иначе возвращает `False`.

`unregister(session)` вызывается при `disconnect`, обрыве связи и в конце
`serve_client`. Под блокировкой он убирает игрока из лобби, удаляет записи
из `players` и `sessions`, освобождает `player_id`.

`_leave_lobby(session)` удаляет участника из лобби. Если остался второй
игрок, он становится хозяином и получает снимок состава в `updates`.
Оставшийся участник также получает системное сообщение в чат о выходе.
Если ушёл последний игрок, удаляются лобби и его история. У вышедшего
очищаются `lobby_id` и очереди сессии. Выход во время подготовки первой карты отменяет запуск. Если участник
вышел во время игры или перехода между картами, лобби переходит в `paused`.

`_snapshot(lobby)` делает копию состояния лобби, включая отдельную копию
словарей `players`, `ready` и `last_scores`. Карта и внутренний список подтверждений
в снимок не входят. Поэтому подготовленное обновление не изменится, если
состав лобби поменяется до отправки.

### Команды лобби

Все команды требуют предварительного `hello` и приходят с топиком `lobby`.

| `cmdid` | `data` | Результат |
| --- | --- | --- |
| `list` | `{}` | `{"ok": true, "lobbies": [...]}` содержит все лобби по порядку номеров. |
| `create` | `{}` | `{"ok": true, "lobby": {...}}` создаёт лобби с именем из ника. |
| `join` | `{"lobby_id": 1}` | `{"ok": true, "lobby": {...}}` или причина отказа. |
| `leave` | `{}` | `{"ok": true}`; оставшийся участник получает `lobby.update`. |
| `update` | `{}` | `{"ok": true}`; текущее состояние отправляется всем участникам. |
| `configure` | `{"name": "Наше лобби", "seed": 42}` | Только хозяин меняет имя и/или seed; ответ `{"ok": true}`. |
| `ready` / `unready` | `{}` | Установить или отменить свою готовность. |
| `start` | `{}` | Только хозяин запускает подготовку; ответ содержит `ok` и `start_id`. |
| `level` | `{"start_id": 1, "level": {...}}` | Хозяин передаёт сгенерированную карту. Вместо карты можно передать `ok: false`. |

`lobby_id` должен быть целым числом, а не строкой или `bool`. Новое лобби
получает следующий номер, имя хозяина и одного участника. Номер не
переиспользуется после удаления лобби.

В лобби помещается максимум два игрока. `join` отклоняется, если лобби
нет, оно заполнено или игрок уже находится в другом лобби. Вход разрешён
только в состояниях `waiting` и `paused`; наблюдателей нет.

Снимок лобби выглядит так:

```json
{
  "lobby_id": 1,
  "name": "Max",
  "seed": null,
  "state": "waiting",
  "start_id": 0,
  "level_num": 0,
  "last_scores": {},
  "ready": {"6a0613": false, "5b71af": false},
  "can_start": false,
  "host_id": "6a0613",
  "players": {
    "6a0613": "Max",
    "5b71af": "Mira"
  }
}
```

`players` хранит ники по ID в порядке входа. `ready` хранит готовность
каждого участника. `can_start` равен true только в состоянии `waiting`,
если участников ровно двое и оба готовы.

`configure` принимает непустое имя и/или целый seed; `null` означает
случайную генерацию. После начала подготовки менять настройки и
готовность нельзя. `update` остаётся доступен. Изменение настроек или
готовности рассылается обоим игрокам и записывается системным сообщением
в чат; повтор без изменения состояния не добавляет сообщение.

### Запуск партии

Все команды подготовки относятся к `lobby`. Направление важно:
`lobby.level` используется и для передачи карты хозяином серверу,
и для рассылки принятой карты сервером игрокам.

1. Хозяин отправляет `lobby.start` с пустым `data`. Сервер проверяет,
   что игроков двое, оба готовы и подготовка ещё не началась.
2. Сервер увеличивает `start_id`, ставит `state="preparing"` и отправляет
   обоим запрос `lobby.prepare` с `lobby_id` и `start_id`.
   Каждый клиент отвечает `resp` с `data={"ok": true}`.
3. После двух подтверждений состояние меняется на `generating`.
   Только хозяину отправляется `lobby.generate`: `lobby_id`, `start_id`,
   `seed`, словарь `players` (ID → ник) и `level_num=0`.
4. Хозяин сразу подтверждает получение `generate`, затем генерирует
   и проверяет карту на своём компьютере через `generate_level`. Готовые данные отправляет отдельным
   запросом `lobby.level` с `start_id` и `level`.
   При ошибке генерации отправляет `{"start_id": 1, "ok": false}`.
5. Сервер проверяет хозяина, этап и номер попытки запуска, наличие
   словаря карты и словаря игроков, совпадение ID игроков карты и лобби.
   Повторно `validate_level` не вызывает. При успехе сохраняет карту, ставит
   `state="loading"` и отправляет обоим `lobby.level` с `lobby_id`,
   `start_id` и `level`. Ответ хозяину на передачу карты — `{"ok": true}`.
6. Только после двух положительных ответов на получение карты сервер
   ставит `state="started"`. Оба получают `lobby.update`, а в чат
   добавляется «Партия началась.». Оба получают начальное `game.update` с ID первого игрока.
   Если только один может шагнуть, первым ходит он. Если шаг доступен обоим,
   сервер выбирает случайно. Когда оба зажаты, выбранный игрок может пропустить ход.

Ответ `ok: true` на исходный `start` означает принятие команды,
а не завершение всей подготовки. О начале партии говорит состояние
`started` в обновлении лобби.

| Состояние | Значение |
| --- | --- |
| `waiting` | Ожидание игроков, настройка и готовность. |
| `preparing` | Ожидание двух подтверждений подготовки. |
| `generating` | Хозяин создаёт карту. |
| `loading` | Карта разослана, сервер ждёт двух подтверждений. |
| `started` | Оба получили карту, подготовка завершена. |
| `paused` | Сервер ждёт замены участника или подтверждения карты после замены. |

`start_id` — номер попытки запуска внутри лобби. Он отличается от `num`,
который нумерует сетевые запросы. После отмены можно повторить `start`:
номер попытки увеличится, поздние ответы прошлой попытки будут проигнорированы.

`start_response` учитывает подтверждения текущего этапа. `_cancel_start`
возвращает лобби в `waiting`, удаляет карту и список подтверждений,
очищает очередь подготовки и сообщает причину в чат. Готовность игроков
при отмене сохраняется. Отмена происходит при отказе клиента,
ошибке карты, сообщении об ошибке генерации или выходе участника.

За повторы при потере ACK отвечает существующий `Protocol`. Если ACK
не пришёл после трёх отправок, соединение закрывается, участник удаляется,
а при подготовке первой карты запуск отменяется. После ACK на `generate` отдельного таймера
генерации пока нет: сервер ждёт карту, сообщение об ошибке либо выход.

В `level` передаётся словарь данных карты: `maze`, `players`,
`exit`, `key`, `monsters`, `bonuses` и при необходимости `freeze_turns`.
Координаты в JSON — списки `[row, col]`. ID допускают символы `0–9`, `a–f`,
чтобы принимать короткие MD5. Корректность лабиринта, размещения объектов
и наличия ключа обеспечивает генерация на компьютере хозяина. Сервер
доверяет этой проверке и проверяет только связь карты с текущим запуском
и участниками лобби. `validate_level` по-прежнему принимает Level или путь
к файлу; поддержку сетевого словаря в эту функцию добавлять не требуется.

### `serve_client(tube)`

Обслуживает одно соединение:

1. Создаёт `Session` и `Protocol`.
2. Перед каждым чтением забирает накопленные `session.updates` под
   блокировкой и отправляет каждый снимок отдельным запросом
   `lobby.update` с данными `{"lobby": ...}`.
   Также забирает `chat_updates` и отправляет пары `(cmd, data)` через
   `protocol.request("chat", cmd, session.player_id, data)`.
   Очередь `start_updates` отправляется аналогично. Локальный словарь
   `start_requests` связывает номер отправленного запроса с лобби,
   попыткой запуска и командой. Ожидания отменённых попыток удаляются
   из этого словаря и из `Protocol.pending`.
3. Вызывает `protocol.receive(session.handle_request,
   session.player_id or "unknown")` для обработки
   одного входящего пакета. Если вернулся ответ на запрос подготовки,
   передаёт его данные в `start_response`.
4. Повторяет цикл, пока не получен `disconnect` и `finished` не стал
   `True`.
5. При `EOFError` или `OSError` завершает цикл. `TimeoutError` также
   попадает в обработку `OSError`. Неожиданная ошибка выводится через
   `print(error, flush=True)`. В `finally` снимается регистрация
   и закрывается соединение.

Обновления не отправляются постоянно: они появляются только после
события, которое добавило запись в `updates`.

### `main_server.py`

Скрипт разбирает аргумент `--port` (по умолчанию 1234), создаёт
`GameServer` и запускает сервер `pwntools` с обработчиком
`game.serve_client`. После запуска печатается строка
`Сервер слушает порт <номер>`. При `--port 0` операционная система
выбирает свободный порт, а фактический номер попадает в эту строку.

Запуск из корня ветки с реализацией:

```bash
python main_server.py --port 1234
```

Для остановки нажмите `Ctrl+C`.

## Сценарий лобби

Пусть Макс создаёт лобби, а Мира входит в него.

1. Макс отправляет `lobby.create`. В ответе он сразу получает снимок
   лобби с одним участником. Отдельное обновление при создании не нужно.
2. Мира отправляет `lobby.join` с номером лобби. В ответе на свой запрос
   она получает полный состав: обоих игроков и ID хозяина.
3. Максу сервер отправляет запрос `lobby.update`: состав изменился,
   в лобби появился второй игрок. Макс подтверждает его обычным `resp`.
4. Если Макс отправит `lobby.update`, текущий состав получат оба
   участника, включая самого Макса. Это удобно, если клиент обновляет
   экран только по `lobby.update`.
5. Если Макс выйдет командой `lobby.leave` или оборвёт соединение,
   Мира станет хозяином и получит `lobby.update` с новым `host_id`.
   Если уйдёт последний игрок, лобби исчезнет из `lobby.list`.

Вошедший игрок не получает отдельный `lobby.update` на свой `join`:
актуальный состав уже лежит в ответе на его запрос. Остальные участники
получают обновление, потому что их запросы к этому событию не относятся.

## Как проверить вручную

Клиентской части пока нет, поэтому для проверки можно отправить пакеты
через `pwntools`:

```python
import hashlib

from pwn import remote

from minotaur.online.protocol import encode_packet, read_packet

nick = "Max"
player_id = hashlib.md5(nick.encode("utf-8")).hexdigest()[:6]
tube = remote("127.0.0.1", 1234)

hello = dict(num=1, type="req", topic="system", cmdid="hello",
             id=player_id, data={"nick": nick})
tube.sendline(encode_packet(hello))
print(read_packet(tube, 2))

bye = dict(num=2, type="req", topic="system", cmdid="disconnect",
           id=player_id, data={})
tube.sendline(encode_packet(bye))
print(read_packet(tube, 2))
tube.close()
```

Сервер ответит на `hello` и `disconnect` пакетами `resp`. Для полноценной
игры с лобби и обновлениями нужен цикл чтения, который подтверждает
входящие `lobby.update`. Готовый клиент появится в `client.py`.

## Чат

История хранится в памяти сервера отдельно для каждого лобби. Она удаляется
вместе с пустым лобби. При остановке сервера история теряется.

| Направление | Команда | Данные и результат |
| --- | --- | --- |
| Клиент → сервер | `chat.send` | `{"message": "Привет"}`; ответ содержит `ok` и `message_id`. |
| Клиент → сервер | `chat.history` | `{}`; ответ содержит `ok`, `lobby_id` и список `messages`. |
| Сервер → клиент | `chat.recv` | `lobby_id` и запись `message`. Клиент подтверждает запрос через `resp`. |
| Сервер → клиент | `chat.history` | `lobby_id` и список `messages`. Автоматически отправляется вошедшему игроку и требует ACK. |

Запись сообщения имеет вид:

```json
{"message_id": 1, "from": "6a0613", "message": "Привет"}
```

`message_id` нумерует сообщения внутри лобби. `num` нумерует сетевые
запросы внутри соединения. Автор сообщения указан в `from`, а поле
`id` внешнего серверного пакета содержит ID получателя.
Системные сообщения имеют `from: null`: вход, выход, изменение настроек,
готовность, отмена подготовки, начало партии и автоматическая пауза
при выходе участника из начатой партии.

`chat_command(session, cmd, data)` берёт лобби из сессии отправителя.
Отправитель получает ответ на `send`, а все участники его лобби,
включая автора, получают `chat.recv`. Пустая строка, строка из пробелов
и значение другого типа получают отказ `InvalidMessage`.

`_chat_message(lobby, player_id, text)` вызывается под блокировкой.
Она добавляет запись в `histories[lobby_id]`, затем помещает пару
`("recv", data)` в `chat_updates` каждого участника этого лобби.
Цикл соединения забирает подготовленные пары и отправляет их через
`Protocol.request`. Протокол обслуживает подтверждения и повторы.

При входе игроку сначала подготавливается копия списка прошлых сообщений,
затем всем участникам добавляется сообщение о входе. Новый игрок получает
историю до своего входа и отдельное уведомление о входе. При выходе
сообщение получают оставшиеся участники. Повтор исходного `send` с тем же
`num` получает прежний ответ и сохраняет одну запись в истории.

### Сообщение об автоматической паузе

Если участник выходит через `lobby.leave`, `system.disconnect` или теряет
соединение во время начатой партии, `_leave_lobby` переводит лобби
из `started` в `paused`. Оставшийся игрок получает два сообщения:

1. «Игрок <ник> вышел из лобби.»
2. «Партия на паузе: ждём второго игрока.»

Оба сообщения отправляются обычным `chat.recv`, имеют `from: null`,
собственные `message_id` и сохраняются в истории этого лобби.
Повторы и ACK обслуживаются тем же протоколом, что и сообщения игроков.
Ушедшему игроку уведомления не отправляются. При выходе до начала партии
или из уже приостановленной партии новое сообщение о паузе не создаётся.

Вошедший получает историю чата и текущее состояние игры.

## Игровые команды и замена участника

| Направление | Команда | Данные и результат |
| --- | --- | --- |
| Клиент → сервер | `game.move` | Например, `{"direction": "right"}`. Допустимы up, down, left, right. |
| Клиент → сервер | `game.skip` | `{}`. Пробел расходует действие в раунде. |
| Сервер → оба | `game.update` | Полная карта, игроки, очередь (`next_player_id`), раунд, результат и список вышедших с карты (`escaped`). Каждый отвечает обычным resp. |
| Клиент → сервер | `game.sync` | `{}`. Участник, от которого ждут ACK, повторно получает текущий снимок. |

Сервер принимает ход по очереди после двух подтверждений предыдущего снимка.
При недопустимом ходе он возвращает `InvalidMove` и оставляет очередь игроку.
При успехе отправитель получает `{"ok": true}`, затем оба получают снимок.
Монстры действуют после завершения раунда. Ключ общий. Первый вышедший ждёт
в безопасности, второй может продолжать. Если один вышел и второй погиб,
уровень пройден для обоих, очки за прохождение получает вышедший.

### Переход на следующую карту и конец партии

На уровнях 1–6 сервер ждёт от обоих ACK на итоговое `game.update` со
статусом `Win`. Затем увеличивает `start_id` и отправляет хозяину
`lobby.generate` с индексом следующей карты (`level_num` от 1 до 6).
Повторно нажимать «Готов» и «Старт» не требуется. Хозяин присылает карту
через `lobby.level`. Оба подтверждают её получение и получают начальное
`game.update`. Оба начинают уровень живыми, с личными очками с прошлой карты.

Если участник выходит во время генерации или загрузки следующей карты,
сервер сохраняет результат пройденного уровня. Когда на свободное место
входит игрок, оба подтверждают этот результат, и хозяин получает новый
запрос генерации.

После седьмой победы или общего поражения оба подтверждают итоговое
`game.update` и остаются в том же лобби. В `lobby.update` приходит
`state="waiting"`, готовность обоих сброшена. Словарь `last_scores`
содержит итоговые очки по ID игроков и пуст до окончания первой партии.
Для новой партии оба снова нажимают «Готов», хозяин нажимает «Старт».
Новая партия начинается с первой карты и с нулевыми очками.

Если клиент подтвердил пакет ответом `{"ok": false}`, он сохраняет
соединение и место. Сервер ждёт применения снимка. По запросу `game.sync`
он отправляет этому клиенту новый сетевой запрос с тем же `update_id`.
Уже полученное подтверждение напарника сохраняется. При отсутствии
ожидаемого обновления сервер отвечает `NoPendingUpdate`, вне лобби — `NotInLobby`.
Если ответ вообще не пришёл, действуют обычные повторы и таймаут протокола.

Когда игрок покидает партию, сервер запоминает его ID в `vacant_id`.
Оставшийся ждёт. По `lobby.join` новый участник получает роль прежнего
игрока, включая позицию, очки, бонусы и состояние гибели или выхода с карты.
Если прежний участник уже ходил в этом раунде, действие остаётся учтённым.
Оба получают новый снимок. Когда оба подтвердят его, сервер автоматически
продолжит игру. Меню Esc относится к клиентскому интерфейсу: пока игрок
в меню, клиент продолжает получать пакеты и подтверждать их. Таймера хода нет.

## Ошибки и тестирование

Ошибки имеют `ok: false`, текст `error` и код `error_code`.
Клиент может выбирать действие по коду и показывать пользователю текст.

| Код | Причина |
| --- | --- |
| `InvalidJson` | Строка содержит некорректный JSON. |
| `InvalidEncoding` | Строка не декодируется как UTF-8. |
| `InvalidNum` | Поле num отсутствует, имеет неверный тип или меньше 1. |
| `InvalidFields` | Неверный набор полей, пустой или нестроковый id либо cmdid. |
| `InvalidType` | type отличается от req и resp. |
| `UnknownTopic` | Неизвестный топик. |
| `InvalidData` | data должен быть объектом JSON. |
| `NumAlreadyUsed` | Под уже принятым номером пришёл другой запрос. |

`read_packet` сообщает об ошибках входящего пакета через `PacketError`
из `minotaur/exceptions.py`. `receive` перехватывает исключение,
отправляет собственный запрос `system.error` и продолжает работу.
Клиент подтверждает уведомление обычным `resp`. До регистрации сервер
использует `id="unknown"`, после регистрации передаёт ID из сессии.

При `NumAlreadyUsed` сервер отправляет отказ `resp` с полями
исходного запроса. Прежняя запись в `answers` сохраняется.
Для `InvalidNum` и `NumAlreadyUsed` в `data` добавляется
`next_num`: максимальный номер принятого запроса этого соединения плюс 1.
До первого принятого запроса подсказка равна 1.
Для остальных ошибок поле `next_num` отсутствует.

```json
{"ok": false, "error": "Номер уже использован другим запросом.", "error_code": "NumAlreadyUsed", "next_num": 21}
```

Обычный отказ в команде приходит как `resp`. Используются коды
`InvalidNick`, `InvalidPlayerId`, `PlayerAlreadyConnected`,
`HelloRequired`, `WrongPlayerId`, `UnknownCommand`, `NotInLobby`,
`AlreadyInLobby`, `LobbyNotFound`, `LobbyFull` и `InvalidMessage`.

Для настроек и запуска добавлены:

| Код | Причина |
| --- | --- |
| `HostRequired` | Команда доступна только хозяину лобби. |
| `InvalidSettings` | Не переданы name/seed либо есть лишние поля. |
| `InvalidLobbyName` | Имя пустое или не является строкой. |
| `InvalidSeed` | Seed не целое число и не null. |
| `CannotStart` | Нет двух готовых игроков либо запуск уже начался. |
| `LobbyLocked` | На текущем этапе нельзя менять настройки/готовность или входить. |
| `UnexpectedLevel` | Карта пришла не на этапе генерации или с неверным start_id. |
| `InvalidLevel` | Нет словаря карты/игроков или ID не совпадают с лобби; подготовка отменяется. |

После такого ответа соединение продолжает работать.

При закрытии связи возникает `EOFError` или `OSError`.
После исчерпания попыток получить ACK протокол закрывает соединение
с `TimeoutError`. Неожиданные ошибки кода сервер печатает в stdout
и завершает соответствующий сеанс. Вывод можно перенаправить при запуске.

Тесты протокола проверяют запросы, ответы, проверку пакетов и повторную
доставку. При конфликте номеров проверяется отказ, сохранение прежнего
ACK и обработка нового запроса с предложенным номером.

В `test_online_server.py` шесть обычных тестов напрямую вызывают
`register`, `handle_request` и `lobby_command`. Для каждого метода есть
успешный и ошибочный случай. Тесты также проверяют очистку регистрации,
рассылку обновлений и передачу прав хозяина.

В `test_online_chat.py` проверяются изоляция чата, история и повторы.
В `test_online_game.py` проверяются ходы и ACK, победа и поражение,
повторная доставка через sync, замена участника, выбор первого хода в тупике
и переход через все семь карт с сохранением личных очков.

В `test_online_lobby_settings.py` проверяются настройки и готовность,
в `test_online_start.py` — успешная цепочка запуска, отказы, чужие ID в карте,
ошибка генерации, отмена, отключение и устаревшее подтверждение.

Запуск проверок из корня ветки с реализацией:

```bash
python -m pytest -k online
python -m pytest
python -m flake8 main.py main_server.py minotaur tests
```

## Готовность топиков и следующие этапы

| Топик | Что готово на сервере | Что осталось |
| --- | --- | --- |
| `system` | `hello`, `disconnect`, уведомление `error`. | `ping` отдельно не реализован: доступность проверяется подключением. |
| `chat` | `send`, `recv`, `history`, изоляция лобби, системные сообщения. | Подключить чат к интерфейсу клиента. |
| `lobby` | `list`, `create`, `join`, `leave`, `update`, `configure`, `ready`, `unready`, цепочка `start`. | Подключение будущего клиента к готовым обработчикам. |
| `game` | `move`, `skip`, `update`, `sync`, замена игрока, семь уровней и итоговые очки в лобби. | Проверить всю партию с двумя сетевыми клиентами. |

Клиентская часть и подключение к игровому интерфейсу ещё предстоят.
Запрос генерации хозяину уже есть, но готового клиентского обработчика,
который вызывает генератор и отправляет карту, пока нет. Наблюдателей нет.
Сохранение и продолжение партии из файла по актуальному ТЗ предусмотрены
только для одиночной игры; сетевые save/load не добавляются.
