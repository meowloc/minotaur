# Как работать с репозиторием «Минотавра»

## 1. Разовая настройка

Скачать проект и поставить зависимости.

~~~
git clone https://github.com/meowloc/minotaur.git
cd minotaur
python -m venv .venv
~~~

Затем активируйте окружение: в Windows командой `.venv\Scripts\activate`, в Linux и macOS командой `source .venv/bin/activate`. После этого:

~~~
pip install -r requirements-dev.txt
pytest
~~~

- `git clone` скачивает репозиторий со всей историей.
- `python -m venv .venv` создаёт виртуальное окружение: отдельную папку с библиотеками проекта, чтобы они не смешивались с системными. Папка `.venv` уже есть в `.gitignore`, в репозиторий она не попадёт.
- Активировать окружение нужно в каждом новом окне терминала, иначе pip и pytest будут работать с системным Python.
- `pytest` в конце проверяет, что всё установилось: тесты должны пройти.

**Вход в GitHub.** При первом `git push` GitHub попросит авторизоваться. Пароль от аккаунта не подойдёт: для git GitHub его не принимает. В Git для Windows само откроется окно входа через браузер. В Linux проще всего поставить GitHub CLI и один раз выполнить `gh auth login`.

## 2. Ветки

- `main`: только сдаваемые версии. Сюда сливаем `dev` перед защитой, больше ничего.
- `dev`: общая рабочая ветка. В ней всегда должна лежать работающая игра.
- `feature/<задача>`: своя ветка на каждую задачу из ТЗ: `feature/maze-generator`, `feature/bfs`, `feature/records`. Для исправления ошибки: `fix/<что-чиним>`. Имена пишем латиницей через дефис.

Пушить напрямую в `main` и `dev` нельзя, GitHub это заблокирует: изменения попадают туда только через pull request.

**Удалять слитые ветки запрещено!!** Не нажимайте «Delete branch» после слияния и не используйте `git branch -d` и `git push origin --delete`.

## 3. Работа над задачей

Одна задача из ТЗ – одна ветка – один pull request. Порядок всегда одинаковый.

**Шаг 1. Обновить dev.**

~~~
git checkout dev
git pull
~~~

Новая ветка должна начинаться от свежей `dev`. Иначе вы будете писать код поверх устаревшей версии и потом разбирать конфликты.

**Шаг 2. Создать свою ветку.**

~~~
git checkout -b feature/bfs
~~~

`-b` создаёт ветку от текущей (`dev`) и сразу на неё переключает.

**Шаг 3. Писать код вместе с тестами и docstrings, коммитить по ходу.**

~~~
git status
git add minotaur/pathfinding.py tests/test_pathfinding.py
git commit -m "feat(pathfinding): add bfs_distances"
~~~

- `git status` показывает, какие файлы изменились и что уже подготовлено к коммиту. Смотрите его перед каждым коммитом.
- `git add <файлы>` добавляет в коммит конкретные файлы. Лучше перечислять их явно, а не писать `git add .`: так в коммит не попадёт ничего случайного.
- Если добавили лишнее: `git restore --staged <файл>` убирает файл из подготовленных, не трогая изменения в нём.
- `git commit -m "..."` сохраняет коммит с сообщением. Как писать сообщения: в разделе 4.

**Шаг 4. Проверить перед отправкой.**

~~~
pytest
flake8 main.py minotaur tests
~~~

Обе команды должны пройти без ошибок. flake8 запускаем только на папках проекта: на весь корень его не натравливайте, иначе он полезет проверять библиотеки внутри `.venv`.

**Шаг 5. Подтянуть свежую dev и отправить ветку на GitHub.**

~~~
git merge dev
git push -u origin feature/bfs
~~~

`-u` связывает локальную ветку с удалённой. Дальше в этой ветке достаточно писать просто `git push`. Если после `git merge dev` появились конфликты, решите их по разделу 5 до отправки.

**Шаг 6. Открыть pull request.** На странице репозитория появится кнопка «Compare & pull request». Проверьте, что слияние идёт в `dev` (поле base: dev), заполните шаблон описания (что сделано, как проверить, чек-лист).

**Ревьювером обязательно назначьте Kolya080808 или meowloc** (справа в поле Reviewers). Они назначаются автоматически через CODEOWNERS, но проверьте, что так и произошло. Если автор PR сам один из них, ревьювером назначается другой. PR без одобрения одного из них не сливаем.

**Шаг 7. Слить после одобрения.** Когда ревьювер нажал «Approve» и проверка CI зелёная, нажмите «Merge pull request». Ветку после слияния не удаляйте.

**Шаг 8. Вернуться в обновлённую dev.**

~~~
git checkout dev
git pull
~~~

Теперь в `dev` есть ваша работа. Следующую задачу начинайте снова с шага 2.

## 4. Правила коммитов

- **Маленькие коммиты.** Один коммит – одно законченное изменение: добавили функцию с тестами, исправили ошибку, дописали документацию. Коммитьте каждый раз, когда что-то заработало, а не раз в неделю.
- **Понятные сообщения.** Формат: `тип(модуль): что сделано`. Язык выберите один на всю команду, примеры ниже на английском.
- **Только свой код.** На защите каждый отвечает за свой код, и история коммитов показывает, кто что писал. Чужие модули без договорённости не правим: нужна правка – попросите автора.
- **Общие файлы по договорённости.** `constants.py` и `exceptions.py` меняются отдельным маленьким pull request, о котором знает вся команда. Так меньше конфликтов.
- **Что не коммитим:** папку `.venv`, `__pycache__`, настройки редакторов (`.idea`, `.vscode`), любые пароли и токены. Большая часть этого уже в `.gitignore`, но перед коммитом всё равно смотрите `git status`.

| Тип | Когда | Пример |
| --- | --- | --- |
| feat | Новый функционал | feat(generator): add add_loops |
| fix | Исправление ошибки | fix(monsters): stop hunter walking through walls |
| test | Только тесты | test(records): cover broken file case |
| docs | Документация, README | docs: add install section to README |
| refactor | Переписали код, поведение не изменилось | refactor(game): extract check_collision |
| style | Форматирование под PEP-8 | style: fix flake8 warnings in render |
| chore | Служебное: зависимости, настройки | chore: add readchar to requirements |

## 5. Ревью и конфликты

**Ревью.** Если вас назначили ревьюером, посмотрите PR в течение двух суток: остальные ждут. Проверьте, что код понятен, тесты есть и проходят, flake8 не выдаёт замечаний, у новых функций есть docstrings. Всё хорошо – «Approve», есть замечания – «Request changes» с комментариями к конкретным строкам. Заодно так вы узнаёте, как устроены чужие части.

**Конфликты.** Конфликт возникает, когда в `dev` и в вашей ветке изменили одни и те же строки. GitHub тогда не даст слить PR. Решение – подтянуть свежую `dev` в свою ветку:

~~~
git checkout dev
git pull
git checkout feature/bfs
git merge dev
~~~

Git отметит спорные места прямо в файлах:

~~~
<<<<<<< HEAD
ваш вариант
=======
вариант из dev
>>>>>>> dev
~~~

Оставьте нужный код, удалите строки-маркеры, затем `git add` для исправленных файлов и `git commit`. Если не уверены, какой вариант правильный, спросите автора второго изменения, а не выбирайте наугад.
